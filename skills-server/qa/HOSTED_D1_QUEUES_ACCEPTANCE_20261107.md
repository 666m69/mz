**Architecture of this acceptance:** A private Cloudflare Queue was sent a single authorized `init` message via Cloudflare's account API. The Queue consumer then triggered each subsequent phase automatically **only after the preceding phase succeeded**, without public HTTP exposure. Temporary owner/runner/data/capability credentials were generated for this QA Worker alone and stored as Cloudflare secret bindings; no real user credentials were used.

**Access remained intact.** No Cloudflare Access policy was edited, weakened or bypassed. The test Worker had no public Workers.dev subdomain. No ChatGPT Work plan, paid service, browser login or user SQL intervention was required.

## Problems surfaced and fixed

1. The original QA harness tried executing complete SQL migration files through `D1.exec`; hosted D1 returned `D1_EXEC_ERROR`. Added `migrationStatements()` to separate the source-pinned DDL/DML into **30 + 7 + 3** complete top-level statements and apply each with `db.prepare(statement).run()`, retaining trigger bodies.
2. First disposable Worker used hex-encoded keys, whereas `security.mjs` requires exactly **43-character Base64URL strings** for 32-byte `DATA_KEY` and `CAPABILITY_KEY`. Hardened QA preflight and regenerated correct, separate keys.
3. KV read propagation initially delayed results. Changed the Queue consumer to self-chain each next phase only upon success; the final `qa-complete` record independently confirmed all phases.

Each failed disposable attempt was terminated and the associated temporary D1 discarded before a clean rerun; real customer data was never touched.
